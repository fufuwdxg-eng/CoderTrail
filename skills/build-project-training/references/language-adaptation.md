# 多语言适配

## 保持不变的规则

语言适配只改变实现惯例、资料来源和验证工具。九维权重、总分至少 85、单维下限、真实运行证据、许可检查、研究广度、去重阈值、覆盖增量、默认 15 题和用户选择的基础/进阶配比（未指定时 3/12）、文末完整参考代码等规则全部保持不变。

默认由用户指定语言；其次沿用当前任务明确语言；两者均无时使用 Python 并说明。不要因为题库有 30 道 Python 历史题，就覆盖用户指定的 C++、Go 等语言。语言版本和开发平台按本次约束确定；查阅当前官方文档与实际安装版本，不硬编码“最新版本”。未知版本、无法执行的工具链不填作已验证。

## 组织方式与计数

- `single`：一套聚焦一种语言。使用该语言的生态与表达习惯。
- `mixed`：明确列出本套目标语言。可将不同题分配给不同语言，也可让一个项目的组件使用不同语言。基础/进阶配比按整套题目总数计算，不按语言分别重复分配；每题标明哪些语言负责什么组件。
- 一个题目如果提供同一合同的多个语言版本，它们属于同一道题；逐版本复评与测试。同一协作项目按完整交付计一题，需要接口和集成测试。不可用只通过的一个组件代表整个项目通过。
- 不强制学习者先掌握整套所有语言：总览按语言列先修知识、运行环境和建议路线。少量新增生态知识可在题目前说明，不能把陌生安装流程当成主要难度。

在 `language_context` 固定目标语言、模式、选择依据和工具链；在每题 `implementation_languages`、每份评估的 `source.languages` 填实际范围。C 与 C++、JavaScript 与 TypeScript 分开记录，框架、运行时、构建工具不是语言。SQL 应另注明数据库与方言。

## 常见语言的证据适配

下表是适配检查入口，不是强制使用全部工具。按规模选择一种适合的测试方案，查阅对应版本官方文档，执行真实命令。所有语言都须验证行为；不能因缺少某个测试框架就免测。未列出的语言按下一节扩展。

| 语言 ID | 环境与交付信息 | 在原九维框架内特别检查 | 执行证据示例 |
| --- | --- | --- | --- |
| `python` | 解释器、隔离环境、依赖清单、入口 | 可变对象、类型边界、异常与资源关闭 | 标准库 unittest 或已固定版本的 pytest，运行实际样例 |
| `javascript` | Node.js 或浏览器、模块模式、依赖锁定文件 | 数值精度、异步任务、错误传播、DOM 或事件循环 | Node 场景可用 `node --test`；浏览器项目实际做浏览器行为验证 |
| `typescript` | TypeScript 版本、tsconfig、运行时和构建路径 | 类型与运行时边界、外部数据校验、异步生命周期 | 类型检查加运行时测试；`noEmit` 只检查类型不提供运行验证 |
| `c` | 编译器、C 标准、头文件、构建和链接方式 | 内存边界、溢出、指针生命周期、返回码、资源释放 | 编译警告检查加可执行测试；适用且环境支持时加内存检查 |
| `cpp` | 编译器、C++ 标准、构建配置、必要库 | RAII、所有权、对象寿命、异常安全、并发与未定义行为 | 编译并运行测试；采用 CMake/CTest 的项目记录构建配置及真实用例结果 |
| `java` | JDK、包目录、选定构建工具与依赖 | 集合与对象相等、异常、资源关闭、线程同步 | 项目现有的 Maven/Gradle 测试任务或独立可执行测试；不混用无效命令 |
| `csharp` | .NET SDK、目标框架、项目文件 | 可空引用、异步取消、Dispose、异常与并发 | 对应项目的 `dotnet test` 或可执行测试，并记录测试运行器 |
| `go` | Go 版本、模块文件、包目录 | error 处理、goroutine 生命周期、context 取消、竞态 | `go test ./...`；适用并受环境支持时另加竞态检测 |
| `rust` | rustc、edition、Cargo 清单和依赖 | 所有权、Result、panic 边界、unsafe 约束、并发 | `cargo test` 加实际示例运行；编译通过不能替代合同验证 |
| `sql` | 数据库引擎/版本、方言、建表与初始化数据 | NULL、排序确定性、事务隔离、约束、参数绑定 | 在隔离测试库执行查询与事务用例；不以 SQLite 通过代表其他方言 |
| `bash` | shell 版本、系统工具版本、平台 | 引号、空格路径、退出码、管道、幂等与失败清理 | 在临时目录执行测试；静态 shell 检查不能替代运行 |

不把一种语言的习惯强加给其他语言：C 不要求异常机制；Rust 的所有权不是统一加分项；脚本不因缺少类而扣分。评判相同需求是否被清晰、可靠、可测试地实现。性能按规定规模、算法和资源目标评价，不按语言速度排名。

## 添加其他语言

适用于 Kotlin、Swift、Dart、Ruby、PHP、R、Julia 等，或用户之后指定的新语言。无需改九维权重或增加封闭白名单：

1. 查官方语言/工具文档，确定规范语言 ID（小写英文及连字符）、版本、运行平台、文件布局、依赖与许可要求。
2. 选择目标生态中的真实源码，记录构建、运行、测试和适用检查方式；不能把语法近似语言的说明照搬过来。
3. 明确其数值、文本、错误、资源和并发语义，映射到现有九维证据。
4. 检查当前环境能否执行并留存真实日志。仅能交叉编译或需要当前不可用的 SDK/设备时，说明验证边界，未执行部分保留 pending。
5. 用同一记录结构和脚本检查。仅记录元数据不代表已经支持或实测该平台所有项目。

## 跨语言借鉴与去重

优先采用目标语言的惯用实现。多语言题在 `source_language_targets` 中将每个来源 ID 映射到实际借鉴它的组件/版本所用语言，合起来覆盖本题全部语言；单语言题可省略，默认来源用于该语言。不要要求仅服务于 Go 后端的来源也被移植到 TypeScript 前端。

确有学习价值时可借鉴其他语言的合格来源，记录 `cross_language_adaptations`：source_review_id、target_languages、semantic_risks、verification_plan。针对该来源实际支撑且源代码语言未覆盖的目标语言，说明语义差异与独立验证计划；这个记录不免除目标语言实现的单独评分与运行。

至少检查整数范围与除法、浮点误差、Unicode/字节索引、集合顺序、相等与哈希、复制/引用/所有权、异常或错误值、资源生命周期、异步/并发模型。按实际采用范围选检查项，不机械要求所有项目都涉及并发。

文本和数值合同应明确空输入、允许的空白与数字字符、编码、前导零、范围和溢出处理；不能让语言默认解析规则替代需求。对照测试可以复用输入合同和独立期望，但原语言程序不是唯一正确性判据。补充边界或性质检查，避免把来源错误照搬。跨组件实现增加协议、序列化、启动顺序、失败传播与集成验收。

跨全部语言历史去重，语言及框架名称不作为领域、概念、成果、工程方法的新增标签。例如把 Python 的路径搜索改成 Java，并没有新的计算问题；只有实际新增的约束、设计目标和可验收工程能力才可能构成新题。所有相似度与覆盖阈值仍按原规则计算。

## 执行与证据

在每份评估的 `verification.language_checks` 中逐语言记录真实环境、运行测试命令、test 类型证据及结果。多语言日志可共用档案，但每项观察须定位到对应语言。编译、类型检查、格式检查和测试的结果分开说明；命令退出码 0 但未发现/执行测试，不算通过。

`curate_bank.py` 是题库管理工具，需在 Python 3.10 及以上的 Linux/WSL 环境执行；这不是学习者项目的运行环境要求。题库管理脚本不直接执行目标项目；配套 project_grader.py 在已准备的环境执行并采集证据，不安装编译器，不提供恶意代码沙箱。使用真实工具链，审阅日志后补充九维判断。

原有未标语言的题库记录先从真实材料确认语言再补字段；不能一律猜为 Python。已有 30 道历史题已明确来自两套 Python 文档，可补 Python 元数据，但仍为 `legacy_unreviewed`，不得补评分或通过标记。老评估缺少语言或对应运行证据时按 pending 处理；补充审查后新建版本化评估，不悄悄继承旧分。

评分程序强制核验 collaboration 的集成测试；variants 用 variant_review_ids 关联单语言独立评估，并核对其文件与整体快照一致。缺工具或没有捕获到实际用例保持待验证。
